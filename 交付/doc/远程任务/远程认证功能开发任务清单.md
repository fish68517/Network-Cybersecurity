# 远程认证功能开发任务清单

## 1. 目标说明

本清单用于指导当前 `MedicalSystemDemo` 项目补充“远程认证（Remote Attestation）+ 安全会话（Secure Session）”能力。

本次任务的参考样例为：
- `intel/confidential-computing.sgx/SampleCode/RemoteAttestation`

选择该样例作为主参考的原因是：
- 结构最接近当前项目的 `App + Enclave` 形态
- 样例同时覆盖 `isv_app`、`isv_enclave`、`service_provider`
- 样例不只做 quote 生成，还覆盖“远程证明 + 建立安全会话”的完整流程

需要强调：
- 当前项目已经实现 `Enclave 隔离 + ECall/OCall + Sealing/Unsealing`
- 当前项目尚未实现真正的远程认证
- 远程认证后续必须与当前病历系统业务逻辑结合，而不是单独再做一个无关 demo

## 3. 总体开发策略

建议按三阶段推进，不要一步到位硬接完整 RA。

### 第一阶段：完成“远程认证架构接入骨架”

目标：
- 在当前项目中建立 Remote Attestation 所需的模块边界
- 预留消息结构、认证状态、接口入口
- 不直接破坏现有病历 CRUD 原型

### 第二阶段：完成“参考样例流程迁移”

目标：
- 参考 `SampleCode/RemoteAttestation` 把 enclave 证明流程接入项目
- 建立“宿主 -> Enclave -> 服务提供方”的认证交互链路
- 输出清晰的认证日志

### 第三阶段：完成“病历业务与远程认证绑定”

目标：
- 未通过认证时，不允许执行敏感病历读取或写入
- 通过认证后，才允许患者/医生执行关键敏感操作
- 将“远程认证 + 安全会话 + 密封存储”整合成完整安全链路

## 9. 当前开发风险与注意事项

### 9.1 最大现实限制：当前项目主要处于 Simulation 环境

这一点必须单独强调。

参考样例和 Intel 官方资料都说明：
- 真正的 Remote Attestation 依赖真实 SGX 证明链路
- `Simulation Mode` 下不能等价替代真实远程认证

这意味着：
- 可以先把代码结构、消息流、模块边界搭起来
- 可以先做论文层面的架构补充和接口预留
- 但若要真正“跑通可验证的 RA”，通常仍需要真实硬件和完整证明环境

### 9.2 不建议第一轮就直接上 DCAP 底层库

原因：
- 当前项目是 Windows + 现有控制台原型
- 直接从 `tee.dcap` 底层库起步，改造成本太高
- 第一轮更适合先参考 `SampleCode/RemoteAttestation` 建立清晰的业务级模块边界

### 9.3 不建议把旧 `sgx-ra-sample` 作为主实现路线

原因：
- 该项目已停止维护
- 它更适合作为旧 EPID 路线的消息流参考
- 不适合作为论文主实现路线和后续项目主干

## 11. 阶段性交付建议

为了降低风险，建议把远程认证功能拆成三个可审核节点。

### 节点 A：结构接入完成

验收标准：
- 新增远程认证相关类型、错误码、接口定义
- 工程仍能编译
- 病历现有功能不被破坏

### 节点 B：认证流程原型完成

验收标准：
- 宿主程序可触发远程认证流程
- 可以看到认证消息流日志
- 可区分“未认证 / 认证中 / 已认证 / 认证失败”

### 节点 C：业务绑定完成

验收标准：
- 未认证时，敏感病历接口拒绝访问
- 认证成功后，敏感病历接口恢复可用
- 日志中能清晰说明“先认证，再进入病历访问”

---

## 12. 当前结论

如果后续要在当前项目中补“远程认证功能”，最合理的落地方式不是直接重写整个系统，而是在现有 `App + Enclave + Sealing` 原型基础上，按 `SampleCode/RemoteAttestation` 的结构逐步增加：

1. 远程认证上下文
2. 认证消息接口
3. 服务提供方模块
4. 安全会话状态
5. 认证与病历敏感操作绑定

当前最适合先做的不是直接改代码，而是先按本清单完成模块拆分和文件级规划，确认后再进入正式编码。
