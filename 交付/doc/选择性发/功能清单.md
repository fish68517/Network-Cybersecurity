# 基于开题报告与现有代码的功能清单

## 1. 现有 Demo 基线分析

### 1.1 `MedicalSystemDemo`（Enclave 侧）已具备能力
- 已完成基础 Enclave 工程搭建，具备 EDL、ECall、OCall 的最小闭环。
- 已实现 `ecall_secure_save_record` 入口，可接收患者姓名与诊断结果。
- 已实现 Enclave 内日志输出到宿主侧的 OCall。
- 当前仅为演示逻辑，Enclave 内未真正执行 SGX Sealing、未维护业务数据结构、未提供多用户认证与权限控制。

### 1.2 `MedicalSystemDemo_app`（宿主 App 侧）已具备能力
- 已完成 Enclave 创建、调用、销毁流程。
- 已支持控制台录入患者姓名和诊断结果。
- 已实现模拟演示模式，在 SGX 初始化失败时走 mock 流程。
- 已实现伪“密文文件”输出 `patient_data_encrypted.bin`，可用于演示“非明文落盘”。
- 当前为单机演示程序，不具备客户端/服务端分层、用户体系、真实数据库、真实加密密封、查询修改删除、审计等完整业务能力。

### 1.3 当前 Demo 与开题报告的差距
- 只有“新增一条病历并落盘”的演示，没有完整病历管理流程。
- 没有患者、医生、管理员三类角色模型。
- 没有基于 RSA/ECC 的注册、登录、挑战应答认证。
- 没有患者基本信息管理。
- 没有病历信息 CRUD 与权限校验。
- 没有真实 SGX Sealing/Unsealing 与完整性校验。
- 没有远程证明（Remote Attestation）。
- 没有 Switchless 高性能调用优化。
- 没有审计日志、异常处理、性能测试与对比实验。

## 2. 毕业设计目标功能清单

以下功能清单按照“开题报告 + 任务书 + 现有代码可扩展性”整理，适合作为后续开发范围。

### 模块 A：系统基础与架构重构
1. SGX Enclave 初始化与销毁管理
- 在现有 Enclave 生命周期管理基础上，规范初始化、异常返回、资源释放流程。
- 区分真实 SGX 模式与 Simulation 模式，避免演示逻辑混入正式业务逻辑。

2. 可信区 / 非可信区职责拆分
- `MedicalSystemDemo` 负责敏感数据处理、密钥管理、权限判断、密态数据操作。
- `MedicalSystemDemo_app` 负责输入输出、文件/数据库落盘、网络通信、日志转发。

3. 模块化接口设计
- 按“认证接口、患者信息接口、病历接口、系统接口”拆分 ECall/OCall。
- 将当前单一 `ecall_secure_save_record` 扩展为多业务接口。

### 模块 B：用户与身份认证
4. 角色模型管理
- 管理员：负责系统部署、用户注册、公钥录入、系统维护。
- 医生：可查看患者基本信息，可增删改查病历。
- 患者：可增删改查本人基本信息，可查看本人病历。

5. 用户注册功能
- 管理员为患者和医生创建账户。
- 用户生成 RSA/ECC 密钥对。
- 用户公钥安全注册到 Enclave 白名单或密态用户表。

6. 挑战应答登录认证
- Enclave 生成随机挑战值。
- 用户使用私钥签名挑战值。
- Enclave 验签后建立登录态或会话态。
- 全流程避免口令明文传输。

7. 会话管理与身份上下文
- 为已认证用户生成会话标识。
- 每次业务请求附带身份上下文，由 Enclave 校验权限。

### 模块 C：患者基本信息密态管理
8. 患者基本信息数据模型
- 设计患者基本信息结构：患者ID、姓名、身份证号、性别、年龄、电话、地址、紧急联系人等。
- 在 Enclave 内使用安全数据结构维护明文运行态。

9. 患者基本信息新增
- 支持管理员录入初始患者档案。
- 支持患者补充或完善个人信息。

10. 患者基本信息查询
- 患者仅可查看本人信息。
- 医生可查看授权范围内患者基本信息。

11. 患者基本信息修改
- 患者可修改本人允许变更字段。
- 关键字段修改需做权限控制和审计记录。

12. 患者基本信息删除
- 支持逻辑删除或密态删除。
- 删除操作应做权限校验与审计留痕。

### 模块 D：病历信息全生命周期密态管理
13. 病历数据模型设计
- 设计病历结构：病历ID、患者ID、医生ID、就诊时间、主诉、诊断、处方、检查报告、备注、版本号等。

14. 病历新增
- 医生录入诊断记录、处方信息、检查结论。
- 数据进入 Enclave 后再解密处理与密封存储。

15. 病历查询
- 医生可查询所需患者病历。
- 患者可查询本人病历。
- 查询结果按最小必要原则返回。

16. 病历修改
- 允许医生修改指定病历。
- 保留版本号，支持新旧版本识别。

17. 病历删除
- 允许医生执行删除或归档。
- 可设计为逻辑删除，便于论文展示审计与恢复能力。

18. 病历列表与条件检索
- 按患者ID、医生ID、时间区间、病历ID进行检索。
- 后续可扩展关键词检索，但不建议作为第一阶段核心功能。

### 模块 E：密钥管理与密态存储
19. Enclave 内部密钥管理
- 生成并管理用户认证公钥、数据加密密钥、完整性校验密钥。
- 密钥仅在 Enclave 内使用，不暴露给宿主侧。

20. 真实 Sealing / Unsealing
- 将当前“伪密文写文件”替换为真实 SGX Sealing。
- 支持密态数据持久化和重启后解封恢复。

21. 密文存储格式设计
- 设计密封数据头、版本信息、记录数量、索引信息等结构。
- 区分用户数据文件与病历数据文件。

22. 数据完整性与防篡改
- 为密文增加 MAC、摘要或版本校验。
- 防止密文被替换、回滚、重放。

### 模块 F：访问控制与安全策略
23. 基于角色的访问控制（RBAC）
- 将“谁能查、谁能改、谁能删”固化到 Enclave 内部逻辑。
- 防止宿主 App 绕过权限检查。

24. 细粒度对象级权限控制
- 患者只能访问本人数据。
- 医生只能访问业务授权范围内的患者数据。
- 管理员不得读取病历明文。

25. 输入合法性校验
- 校验字段长度、格式、空值、非法字符。
- 降低缓冲区越界与恶意输入风险。

### 模块 G：远程证明与可信连接
26. 远程证明（Remote Attestation）基础实现
- 客户端验证服务器侧 Enclave 身份。
- 建立“连接到的确实是可信 Enclave”的证明链。

27. 安全信道协商
- 在远程证明后协商会话密钥。
- 用于保护客户端到宿主侧/Enclave 的传输数据。

说明：该模块属于毕业设计加分项和论文亮点，但实现难度高。若时间有限，可先完成“本地可信验证 + 接口预留”，再决定是否做完整 RA 流程。

### 模块 H：性能优化
28. 高频接口调用优化
- 统计新增、查询等接口的 ECall/OCall 次数。
- 减少不必要的跨 Enclave 边界切换。

29. Switchless 调用模式
- 基于开题报告要求，引入 SGX Switchless。
- 对高频查询或批量操作进行优化。

30. 批处理与缓存策略
- 将单条操作扩展为批量查询/批量写入。
- 减少频繁切换带来的性能损耗。

### 模块 I：审计、运维与可展示能力
31. 安全审计日志
- 记录登录、查询、修改、删除、解封失败、权限拒绝等事件。
- 审计日志不记录病历明文。

32. 异常处理与错误码体系
- 对认证失败、权限不足、解封失败、文件损坏、数据不存在等情况定义统一错误码。

33. 演示模式与正式模式分离
- 保留 Demo 展示能力，但需与正式论文实现分层。
- 避免 mock 逻辑影响正式测试结果。

34. 测试与实验支撑
- 功能测试：认证、基本信息 CRUD、病历 CRUD、权限校验。
- 安全测试：验证外部存储仅为密文、管理员不可见明文。
- 性能测试：普通模式与 Switchless 模式对比。

## 3. 建议的分阶段实现顺序

### 第一阶段：先把 Demo 变成“能用的密态病历原型”
- 用户角色模型
- 基本患者信息 CRUD
- 病历 CRUD
- 真实数据结构
- 基础权限校验
- 真实 Sealing/Unsealing
- 文件持久化

### 第二阶段：补齐论文核心亮点
- RSA/ECC 注册与挑战应答认证
- 完整性校验与版本控制
- 审计日志
- 性能测试框架

### 第三阶段：冲刺高质量毕业设计
- Remote Attestation
- Switchless 优化
- 条件检索与批处理
- 更规范的 C/S 结构

## 4. 推荐作为毕业设计验收范围的最小可交付版本

如果要在时间和实现复杂度之间取得平衡，建议至少完成以下 10 项核心功能：
1. Enclave 初始化与宿主通信
2. 三角色模型（管理员/医生/患者）
3. 用户注册与公钥保存
4. 挑战应答登录认证
5. 患者基本信息 CRUD
6. 病历信息 CRUD
7. Enclave 内权限校验
8. 真实 Sealing/Unsealing 持久化
9. 密文文件/数据库存储与完整性校验
10. 基础性能对比或 Switchless 初步实现

## 5. 结论

基于现有 `MedicalSystemDemo` 和 `MedicalSystemDemo_app`，本项目当前处于“SGX 最小闭环演示”阶段。后续应围绕“用户认证、角色授权、患者信息管理、病历密态 CRUD、真实 Sealing、完整性保护、性能优化”七个方向展开，逐步完成从 Demo 到毕业设计成品的升级。
