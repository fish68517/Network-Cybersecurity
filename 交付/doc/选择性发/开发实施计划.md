# 基于现有 SGX Demo 的毕业设计实施计划

## 1. 目标说明

本文档用于把 `功能清单.md` 进一步落地为可执行开发方案，明确：
- 先做什么，后做什么
- 哪些功能适合直接在现有 Demo 上扩展
- 需要新增哪些文件和模块
- 每一阶段完成后能够展示什么结果

当前项目不适合继续把所有逻辑写在两个 `cpp` 文件中。为了后续实现用户认证、病历 CRUD、真实 Sealing、权限控制与性能优化，需要先做结构整理，再逐步完成功能。

## 2. 当前工程结构判断

### 2.1 现有文件职责
- `MedicalSystemDemo/MedicalSystemDemo.cpp`
  - 当前职责：Enclave 内最小业务演示
  - 问题：只有一个保存病历接口，无法承载完整系统逻辑

- `MedicalSystemDemo/MedicalSystemDemo.edl`
  - 当前职责：定义一个 ECall 和一个 OCall
  - 问题：接口过少，无法支持认证、查询、修改、删除、持久化

- `MedicalSystemDemo_app/MedicalSystemDemo_app.cpp`
  - 当前职责：控制台输入、Enclave 初始化、模拟调用、伪密文落盘
  - 问题：UI、流程控制、持久化、mock 逻辑全部耦合在一起

### 2.2 结论
当前工程可继续作为毕业设计基础，但必须完成两类改造：
1. 接口扩展：把单一 ECall 扩展为一组业务接口
2. 代码拆分：把 Enclave 业务、宿主侧流程、持久化与控制台交互拆开

## 3. 推荐的代码结构调整

### 3.1 Enclave 侧建议新增文件
建议在 `MedicalSystemDemo` 目录新增以下文件：

- `enclave_models.h`
  - 定义用户、患者信息、病历、审计日志、错误码等结构体

- `enclave_store.h`
  - 定义 Enclave 内存中的安全数据容器与基础读写接口

- `enclave_store.cpp`
  - 实现用户表、患者表、病历表的增删改查

- `enclave_auth.h`
  - 定义角色枚举、认证上下文、权限判断函数

- `enclave_auth.cpp`
  - 实现注册、登录挑战、验签占位、RBAC 校验

- `enclave_persistence.h`
  - 定义密态持久化和恢复接口

- `enclave_persistence.cpp`
  - 实现 Sealing/Unsealing、序列化、反序列化

- `enclave_service.h`
  - 定义面向 ECall 的业务服务函数

- `enclave_service.cpp`
  - 统一封装患者 CRUD、病历 CRUD、认证与权限校验

说明：如果你希望先快一点推进，也可以先不拆成这么多文件，而是先拆成 3 个文件：
- `MedicalSystemDemo.cpp`
- `enclave_models.h`
- `enclave_service.cpp`
但最终为了论文和后期维护，还是建议按模块拆开。

### 3.2 宿主 App 侧建议新增文件
建议在 `MedicalSystemDemo_app` 目录新增以下文件：

- `app_menu.h`
  - 定义控制台菜单与用户交互入口

- `app_menu.cpp`
  - 实现登录、注册、患者管理、病历管理菜单

- `app_enclave_bridge.h`
  - 封装 ECall 调用，避免 `main` 直接操作所有接口

- `app_enclave_bridge.cpp`
  - 实现具体 ECall 调用和返回结果处理

- `app_storage.h`
  - 定义非可信区文件读写、密文文件落盘、加载函数

- `app_storage.cpp`
  - 实现密文文件保存、读取、备份、路径管理

- `app_types.h`
  - 定义宿主侧通用结构、菜单枚举、显示对象

### 3.3 当前文件保留策略
- `MedicalSystemDemo/MedicalSystemDemo.cpp`
  - 保留为 Enclave 主入口文件，但内部逻辑大幅瘦身，只保留 ECall 封装和模块调用

- `MedicalSystemDemo/MedicalSystemDemo.edl`
  - 保留并扩展

- `MedicalSystemDemo_app/MedicalSystemDemo_app.cpp`
  - 保留为程序主入口，但仅负责启动、主循环、模块初始化

## 4. 第一阶段建议实现范围

第一阶段不要直接做 Remote Attestation，也不要一开始就上 Switchless。先把系统做成“能用的密态病历原型”。

### 4.1 第一阶段目标
完成一个支持三角色、基础认证、患者信息 CRUD、病历 CRUD、密态持久化的控制台系统。

### 4.2 第一阶段交付结果
完成后应能演示以下流程：
1. 管理员初始化系统
2. 管理员创建患者和医生账户
3. 患者登录并查看/修改本人基本信息
4. 医生登录并查看患者信息、录入病历、修改病历、删除病历
5. 患者登录查看自己的病历
6. 系统退出后重新启动，能够从密封文件中恢复数据
7. 外部文件只能看到密文或二进制不可读内容

### 4.3 第一阶段必做功能
- 三角色模型
- 本地用户注册
- 基础登录态
- 患者信息 CRUD
- 病历信息 CRUD
- 基础 RBAC 权限控制
- 真实或准真实密态持久化
- 基础错误码与日志

### 4.4 第一阶段可暂缓功能
- 完整 RSA/ECC 挑战应答认证
- 远程证明
- Switchless
- 网络化客户端/服务端分离
- 复杂条件检索

## 5. 第二阶段建议实现范围

第二阶段用于补齐开题报告中的核心亮点。

### 5.1 第二阶段目标
把“能用原型”升级为“论文可写、答辩可讲”的安全系统。

### 5.2 第二阶段重点功能
- RSA/ECC 公钥注册
- 挑战应答认证
- 审计日志
- 数据完整性校验（MAC/版本号）
- 更规范的异常处理
- 性能测试脚本或测试流程

### 5.3 第二阶段交付结果
- 能展示“非口令明文登录”
- 能展示“越权访问被拒绝”
- 能展示“篡改密文文件后恢复失败”
- 能形成论文中的安全设计章节和实验章节基础素材

## 6. 第三阶段建议实现范围

第三阶段用于冲刺高质量毕业设计和答辩亮点。

### 6.1 第三阶段重点功能
- Remote Attestation
- Switchless 调用优化
- 批量查询 / 批量写入
- 更接近 C/S 的结构调整

### 6.2 第三阶段交付结果
- 能做性能对比实验
- 能做可信链路展示
- 能形成论文中的性能优化与系统增强章节

## 7. EDL 接口扩展建议

当前 EDL 只有一个病历保存接口，明显不够。建议扩展为以下类别。

### 7.1 系统类接口

- `ecall_system_load`
- `ecall_system_flush`
- `ecall_system_reset`

### 7.2 用户认证类接口
- `ecall_register_user`
- `ecall_login_user`
- `ecall_logout_user`
- `ecall_get_user_role`

### 7.3 患者信息类接口
- `ecall_create_patient_profile`
- `ecall_get_patient_profile`
- `ecall_update_patient_profile`
- `ecall_delete_patient_profile`
- `ecall_list_patients`

### 7.4 病历类接口
- `ecall_create_record`
- `ecall_get_record`
- `ecall_update_record`
- `ecall_delete_record`
- `ecall_list_records_by_patient`

- `ocall_print_log`
- `ocall_save_blob`
- `ocall_load_blob`
- `ocall_get_time`

说明：第一阶段可以先只做 `print/save/load` 三类 OCall，不必一开始就扩太多。

## 10. 第一阶段实际开发顺序

建议按下面顺序编码，而不是并行乱改。

1. 先扩展 `EDL`
- 先把未来需要的 ECall/OCall 接口确定下来
- 重新生成 `_t.*` 和 `_u.*`

2. 再做 Enclave 内数据结构
- 用户结构
- 患者结构
- 病历结构
- 统一错误码

3. 再做患者与病历 CRUD
- 先不做公钥认证，先做最小登录态
- 先打通业务主链路

4. 再做持久化
- 先做单文件保存恢复
- 再决定是否拆分多文件

5. 再做宿主侧菜单系统
- 让用户能实际演示不同角色操作

6. 最后再补安全增强
- 挑战应答认证
- MAC/版本校验
- 审计
- Switchless

## 11. 论文视角下的实现优先级

从毕业设计答辩角度，不是所有功能价值相同。建议优先级如下：

### P0：必须完成
- 三角色模型
- 患者信息管理
- 病历信息管理
- Enclave 内权限控制
- 密态存储与恢复

### P1：强烈建议完成
- 基于公钥的身份认证
- 数据完整性校验
- 审计日志
- 性能测试

### P2：高质量加分项
- Remote Attestation
- Switchless
- 更标准的客户端/服务端部署

## 12. 下一步建议

基于当前项目实际情况，下一步最合理的动作不是继续写文档，而是直接开始第一阶段编码。

推荐的下一次代码改造范围：
1. 扩展 `MedicalSystemDemo.edl`
2. 新增 Enclave 内部数据结构
3. 把当前单次保存病历逻辑改造成：
- 用户登录
- 患者信息新增/查询
- 病历新增/查询
- 退出前保存密态数据

这样做的原因很直接：
- 这部分实现难度适中
- 这部分最能体现毕业设计不是 Demo
- 这部分为后续认证、Switchless、RA 提供稳定底座
