# 论文与演示修改思路（SGX 侧重点强化）

## 1. 老师意见的核心含义

老师这次提出的要求，本质上不是让论文“多写一点安全”，而是要求把整篇论文和答辩演示的叙事主线，从“一个带加密存储的病历系统”调整为“一个基于 Intel SGX 的机密计算病历系统”。

也就是说，后续修改不能再把重点放在“能增删查改、能保存文件、文件打开是乱码”这种普通系统视角，而要回答下面几个问题：

1. 为什么一定要用 Intel SGX，而不是普通数据库加密。
2. SGX 在这个系统中到底承担了什么角色。
3. 你具体使用了 SGX 的哪些特性。
4. 这些 SGX 特性如何保护病历数据在“使用中、传输中、存储中”的安全。
5. 你的系统和 SGX 架构之间是什么关系，而不是业务功能和控制台菜单之间是什么关系。

## 2. 现阶段论文存在的关键问题

结合当前论文和代码现状，我判断老师不满意的点主要有 5 个。

### 2.1 论文主线偏“业务系统”，而不是“机密计算系统”

当前论文虽然提到了 SGX、Enclave、Sealing，但主体叙述仍然偏向：
- 医生输入病历
- 系统保存文件
- 文件内容是乱码

这种写法会让老师觉得系统只是“普通存储系统 + 一点加密”，而不是“以 SGX 为核心安全边界的可信执行原型”。

### 2.2 对 SGX 特性的解释不够技术化

例如当前表述容易停留在：
- 文件是乱码
- 数据被加密了
- 有 Enclave

但老师希望你能把这些内容上升为更规范的技术表达，例如：
- 数据为什么在 Enclave 外无法被读取。
- 密封后的数据为什么即使磁盘泄露也不影响安全。
- 使用了什么加密机制和完整性保护机制。
- 信任根来自哪里，攻击者为什么拿不到密钥。

### 2.3 对“远程认证/远程证明/安全信道”的表达缺位

老师明确点到了：
- 患者连接数据库时，要强调远程认证。
- 患者与远程 Enclave 要做认证。
- 要建立安全信道。
- 中间攻击者无法获取信息。

这说明论文中必须补一条“远程访问到 Enclave 的安全链路”，否则系统仍然会被理解成“本地控制台存取文件”。

### 2.4 当前实现和论文表述之间存在边界风险

这一点非常关键。

当前代码已经真实实现的 SGX 相关能力，主要是：
- `sgx_create_enclave` 创建 Enclave
- ECall/OCall 边界交互
- Enclave 内部状态管理
- `sgx_seal_data` / `sgx_unseal_data` 进行密封与恢复
- 外部仅保存密封后的二进制状态文件

但是当前代码 **没有真正实现**：
- Remote Attestation 远程证明
- 基于远程证明协商会话密钥
- 患者与远程 Enclave 的真实安全信道

因此后续论文不能直接把“远程证明、安全信道”写成“已经完成的现有代码事实”，否则答辩时老师一问“具体代码在哪”，你会被动。

### 2.5 演示脚本没有把 SGX 作为主角

当前演示流程更像：
- 初始化系统
- 登录管理员
- 注册医生和患者
- 添加病历
- 查看病历

这能证明业务闭环，但不能证明“SGX 是主角”。

老师担心的就是：如果答辩现场只看到 CRUD 菜单，评委会认为你的系统和普通数据库课程设计没有本质差别。

## 3. 修改总原则

后续修改我建议遵循 3 条原则。

### 3.1 原则一：以 SGX 为主线，业务功能为验证载体

论文表达要从“我做了一个病历系统”改成：
- 我做了一个基于 Intel SGX 的密态病历原型系统；
- 病历管理功能只是用于验证 SGX 安全机制在医疗场景中的落地效果。

也就是说，业务不是主角，SGX 安全能力才是主角。

### 3.2 原则二：严格区分“已实现”和“扩展设计”

凡是当前代码已经实现的，可以明确写成：
- 已实现
- 已验证
- 已测试

凡是当前代码还没有实现，但老师希望看到、论文也必须补的内容，要写成：
- 完整部署架构中应包含
- 本文设计上纳入，但原型阶段未在代码中完全落地
- 作为下一阶段扩展实现

这一条是为了避免论文和实际代码脱节。

### 3.3 原则三：表述必须技术化，而不是现象化

例如不能只写：
- 文件是乱码

应改成：
- Enclave 调用 SGX sealing 接口对系统状态进行密封；
- 密封数据采用 AES-GCM 机密性与完整性保护；
- 密封密钥由 CPU 硬件根秘密派生，外部宿主、操作系统、磁盘管理者都无法直接获得；
- 因此即使密封文件泄露，攻击者也无法恢复病历明文。

## 4. 论文修改思路

我建议把论文修改分成 4 条主线来做。

### 4.1 第一条主线：重写“系统架构”章节，把 SGX 安全链路画出来

当前架构图应该从“App + Enclave + 文件”升级为：
- 患者/医生客户端
- 不可信宿主服务器
- 可信执行环境 Enclave
- 密封存储文件/数据库
- 远程认证与安全信道

论文中要明确说明：
- 宿主程序不可信，只负责转发请求、显示结果、保存密封数据
- Enclave 是唯一可信执行区域
- 明文病历只能在 Enclave 内部出现
- Enclave 外部只允许存在密文或经过授权的展示结果

这里建议新增 2 张图：
1. 基于 SGX 的总体架构图
2. 患者/医生访问远程 Enclave 的安全链路图

注意：第二张图里可以画出 Remote Attestation 和 Secure Channel，但正文必须写明“这是完整部署架构/论文设计目标，其中当前原型已实现本地 Enclave 与密封存储，远程证明部分为后续扩展”。

### 4.2 第二条主线：单独增加“Intel SGX 特性在本系统中的利用”小节

这一节是老师最想看到的。

建议单独列出你实际利用的 SGX 特性：

1. Enclave 隔离执行
- 病历核心数据结构和敏感逻辑放在 Enclave 内部执行。
- 宿主程序不能直接读取 Enclave 内存。

2. ECall / OCall 边界机制
- 通过 EDL 定义可信与非可信边界。
- 宿主只能通过受控接口请求服务。

3. Sealing 密封存储
- 使用 `sgx_seal_data` 和 `sgx_unseal_data` 对 `MsdSystemState` 进行密封与恢复。
- 外部只保存密封 Blob，而不是明文病历。

4. SGX 的“使用中保护”能力
- 敏感数据在普通系统中最大的问题是“处理时必须明文驻留内存”。
- 本系统通过 Enclave 将明文处理限制在可信执行区内部。

5. 远程证明与安全信道的目标架构
- 虽然当前代码未完整落地，但论文需要把这一部分作为面向真实部署的关键安全链路写清楚。

### 4.3 第三条主线：把“密封存储”写深，而不是只写“乱码”

这一部分老师已经点得非常明确。

建议后续论文表达改成下面这种层次：

第一层：机制
- Enclave 通过 SGX sealing 机制对系统状态进行密封。
- 密封数据的机密性和完整性由 AES-GCM 提供。

第二层：密钥来源
- 密封密钥不是应用自己硬编码的，也不是宿主程序传进来的。
- 密钥由 SGX 硬件根秘密结合 Enclave 身份信息派生。
- 外部操作系统、管理员、数据库管理者无法直接获得该密钥。

第三层：安全结论
- 即使密封文件、数据库文件或整个磁盘被复制，攻击者也只能拿到密文 Blob。
- 在没有对应合法 Enclave 环境与派生密钥的前提下，无法恢复病历明文。

第四层：你的系统落点
- 你当前项目不是“普通数据库加密”，而是“密封后的 Enclave 状态外置存储”。
- 真正掌握明文和密钥的是 Enclave，不是数据库。

这里要特别注意一个表述边界：
- 可以强调“当前原型通过 SGX sealing API 完成密封”
- 不建议把“RSK”作为正文核心术语反复使用
- 更稳妥的写法是“CPU 硬件根秘密/硬件根信任基础派生的密封密钥”

### 4.4 第四条主线：把“远程认证”写成完整部署架构，而不是硬说已实现

这是最容易出问题的地方。

老师希望你讲：
- 患者连接数据库时，要强调远程认证
- 患者与远程 Enclave 做认证
- 建立安全信道
- 中间攻击者无法获取任何信息

但从代码事实看，你当前没有真正实现 Remote Attestation。

因此我建议论文采用下面这种写法：

#### 推荐写法
- 在完整部署场景中，患者客户端在发送病历请求前，需要先对服务器端 Enclave 发起远程证明验证；
- 客户端验证 Enclave 身份和测量值后，再与可信 Enclave 建立安全信道；
- 这样可以防止中间人伪造服务端或将请求导向恶意宿主；
- 本文当前原型由于运行于 SGX Simulation 环境，重点完成了 Enclave 隔离、ECall/OCall 边界和密封存储原型验证；远程证明与安全信道作为面向真实部署的下一阶段扩展模块进行设计说明。

#### 不建议写法
- 患者与远程 Enclave 已经完成远程证明并建立安全信道。

因为这句话一旦写死，答辩时老师很可能继续追问：
- 用了哪套 RA 流程？
- quote 和 report 在哪？
- session key 怎么协商？
- 代码在哪个文件？

你现在接不住。

## 5. 演示修改思路

演示必须从“业务演示”改成“SGX 能力演示 + 业务验证”。

### 5.1 演示顺序建议调整

当前顺序偏业务，我建议改成：

1. 先展示 Enclave 启动
- 展示 `sgx_create_enclave` 初始化成功
- 强调系统核心逻辑运行在 Enclave 中

2. 再展示密封文件路径
- 展示 `sealed_system_state.bin` 的保存路径
- 强调外部宿主只能看到密封后的二进制 Blob

3. 再展示文件不可读
- 可以用十六进制查看器或记事本打开 `sealed_system_state.bin`
- 但讲解重点不是“乱码”，而是“密封后的二进制密文，外部无法解析”

4. 再展示业务操作
- 管理员注册用户
- 医生新增病历
- 患者查看病历

5. 最后回到 SGX 安全结论
- 明文处理发生在 Enclave 内部
- 外部存储是密封后的密文
- 宿主层只负责调用接口和保存 Blob

### 5.2 演示时必须口头强调的句子

后续答辩你需要反复强调：

- “这个系统的重点不是菜单，而是敏感数据始终被限制在 Enclave 可信边界内处理。”
- “宿主程序是不可信的，真正可信的是 Enclave。”
- “外部文件不是明文病历，而是经过 SGX sealing 后的密封状态。”
- “即使磁盘被拷走，攻击者拿到的也是密封 Blob，而不是病历明文。”
- “在完整部署场景下，客户端应先通过远程证明验证远程 Enclave，再建立安全信道。”

### 5.3 如果要进一步提高演示说服力，建议补 3 个小增强

这部分不是现在立刻改，而是思路里建议。

1. 增加更明确的 SGX 日志
- 例如打印：`调用 sgx_create_enclave`、`调用 sgx_seal_data`、`调用 sgx_unseal_data`
- 这样评委不会只看到业务菜单

2. 增加一张“数据流向图”
- 输入明文 -> ECall -> Enclave 内处理 -> Sealing -> 密文落盘

3. 增加一张“威胁模型图”
- OS 不可信
- 磁盘泄露不可信
- 宿主程序不可信
- 只有 Enclave 为可信边界

## 6. 论文中哪些地方建议重点改写

我建议优先改这几个部分：

### 6.1 第一章 绪论

要把“为什么是 SGX”写得更强：
- 传统加密只能保护静态和传输态，不能保护使用中的明文
- SGX 解决的是“使用中数据保护”问题
- 所以本系统的创新点不在普通 CRUD，而在机密计算执行环境

### 6.2 第三章 系统设计

这一章应成为 SGX 重点章节：
- 系统总体架构
- 信任边界划分
- ECall/OCall 接口设计
- Sealing 机制设计
- 远程证明与安全信道设计
- 威胁模型与安全目标

### 6.3 第四章 系统实现

这一章要把你的代码和 SGX API 对上：
- `sgx_create_enclave`
- `sgx_seal_data`
- `sgx_unseal_data`
- `ecall_system_flush`
- `ecall_system_load`
- `ocall_save_blob`
- `ocall_load_blob`

要让评委看到：
- 不是在泛泛谈 SGX
- 而是你的代码里确实调用了这些接口

### 6.4 第五章 系统测试与安全性分析

当前不能只证明“功能能跑通”，还要证明：
- 外部文件中不存在病历明文
- 数据恢复必须经过 Enclave 解封
- 宿主程序本身不掌握密钥
- 如果磁盘泄露，攻击者面对的是密封密文

同时要把“远程证明尚未在 Simulation 原型中完整实现”写成限制与展望，而不是回避不写。

## 7. 我建议采用的最终修改策略

我建议采用“保守而有说服力”的版本，而不是“过度包装”的版本。

### 7.1 保守而有说服力的版本

核心做法：
- 强化已实现的 SGX 内容：Enclave 隔离、边界接口、Sealing、密封文件、威胁模型。
- 把远程证明、安全信道写成完整部署架构和下一阶段扩展。
- 演示中突出 SGX API、Enclave、密封文件和不可信宿主边界。

这种写法的优点是：
- 真实
- 不怕老师追代码
- 逻辑完整
- 容易自圆其说

### 7.2 不建议采用的版本

不建议把论文改成：
- 已经实现远程证明
- 已经实现患者与远程 Enclave 安全信道
- 已经做完端到端远程认证

因为当前代码支撑不了这个说法。

## 8. 具体落地建议

如果你认可这份思路，后续实际修改我建议按这个顺序做：

1. 先改论文整体叙事，把主线换成 SGX 机密计算。

老师这次要求非常明确：
- 不是让你“再加一点安全描述”，

- 架构重心改成 SGX

## 10. 三个 GitHub 远程认证项目分析

本节基于以下三个 GitHub 项目进行分析：

1. `intel/confidential-computing.tee.dcap`
2. `intel/confidential-computing.sgx/SampleCode/RemoteAttestation`
3. `intel/sgx-ra-sample`

### 10.1 `intel/confidential-computing.tee.dcap`

结论：**涉及远程认证，但它更偏底层 DCAP 组件库，不是现成的业务级端到端远程认证工程。**

依据：
- 官方 README 明确写到：Intel SGX DCAP 提供的是面向数据中心、云服务和企业的 SGX attestation support。
- README 同时明确说明：该模型使用的是 **ECDSA**，而不是旧的 **EPID** 客户端模式。
- 项目目录中重点是：`QuoteGeneration`、`QuoteVerification`、`QuoteGenerationSample`、`QuoteVerificationSample`、`QuoteAppraisalSample`。

说明：
- 这个仓库回答的是“如何生成 quote、如何验证 quote、如何做 DCAP 证明链验证”。
- 它并没有直接给出一个像“患者客户端 -> 业务服务器 -> 医疗 Enclave”这样完整的业务远程认证闭环样例。
- 因此它更适合作为 **底层远程认证能力库**，而不是你当前项目最容易直接改造的第一选择。

### 10.2 `intel/confidential-computing.sgx/SampleCode/RemoteAttestation`

结论：**明确涉及远程认证，而且是一个更接近业务接入形态的 SGX 远程认证样例。**

依据：
- 该样例 README 明确写到：
  - “How an application enclave can attest to a remote party”
  - “How an application enclave and the remote party can establish a secure session”
- 目录结构直接包含：
  - `isv_app`
  - `isv_enclave`
  - `service_provider`
- `service_provider` 目录下还包含：
  - `ias_ra.cpp`
  - `network_ra.cpp`
  - `service_provider.cpp`

说明：
- 这个样例不是单独演示 quote 生成，而是完整演示了：
  - 应用侧
  - Enclave 侧
  - 远端服务提供方
  三者之间的远程认证交互。
- 它还进一步强调了：远程认证完成后，可建立 **secure session**。
- 从“业务接入形态”上看，它比 `tee.dcap` 更接近你现在这个项目未来要补的模块。

### 10.3 `intel/sgx-ra-sample`

结论：**明确涉及远程认证，而且是完整的端到端 EPID 远程认证样例；但它已停止维护，并且是较旧的 EPID/IAS 路线。**

依据：
- README 明确写到：
  - “Remote Attestation End-to-End Sample for EPID Attestations”
  - 包含 sample ISV client、client enclave 和 remote attestation server。
- README 还明确写到：
  - 该项目 **will no longer be maintained by Intel**。
- README 同时说明：
  - `Remote Attestation will fail for clients running in simulation mode`。
- README 还特别说明：
  - 样例中的 client/server 网络协议 **no error handling and no encryption**，仅用于演示 RA procedure，不是生产级应用协议。

说明：
- 这个项目的优点是：
  - 是完整的 end-to-end 样例；
  - 还支持 Windows 构建说明；
  - 对你当前 Windows C++ SGX 项目有较强参考价值。
- 但它的问题同样明显：
  - Intel 已停止维护；
  - 使用的是旧的 **EPID + IAS** 路线；
  - 样例网络层没有真正做业务级安全传输封装；
  - 仿真模式下远程认证本身无法成功。

## 11. 三个方案的对比结论

### 11.1 如果只问“这三个项目是否涉及远程认证”

答案是：**三个都涉及远程认证，但层级不同。**

- `intel/confidential-computing.tee.dcap`：涉及，偏 DCAP 底层组件与 quote 验证基础设施。
- `intel/confidential-computing.sgx/SampleCode/RemoteAttestation`：涉及，偏完整样例，展示 enclave 与远端如何认证并建立安全会话。
- `intel/sgx-ra-sample`：涉及，偏完整端到端样例，但属于旧的 EPID/IAS 路线，且已停止维护。

### 11.2 如果只问“哪个最适合直接改造我当前项目”

我的结论是：**最适合作为你当前项目“远程认证功能原型设计参考”的，是 `intel/confidential-computing.sgx/SampleCode/RemoteAttestation`。**

原因如下：

1. 它最接近你当前项目的结构。
- 你现在的项目本质上也是：`App + Enclave + 外部交互`。
- 该样例正好也是：`isv_app + isv_enclave + service_provider`。
- 映射关系自然，容易迁移到你的论文和系统设计中。

2. 它不仅讲 attestation，还讲 secure session。
- 老师强调的不只是“证明一下 Enclave 是真的”，还包括：
  - 患者要和远程 Enclave 认证；
  - 认证后建立安全信道；
  - 中间攻击者拿不到任何信息。
- 这正好对应该样例 README 中“attest + establish secure session”的定位。

3. 它比 `tee.dcap` 更适合做第一步接入设计。
- `tee.dcap` 更底层，适合后期做现代化 DCAP 升级。
- 但如果你现在要给老师解释“远程认证功能怎么加到我的项目里”，`SampleCode/RemoteAttestation` 更容易讲清楚整体流程。

### 11.3 为什么不把 `sgx-ra-sample` 作为第一选择

不是说它没价值，而是它更适合作为“补充参考”，不适合作为你的主选实现路线。

主要原因：
- Intel 已停止维护；
- 它是 **EPID** 路线，不是更现代的数据中心 **DCAP/ECDSA** 路线；
- 样例网络层明确不是生产级安全协议；
- 仿真模式不能真正跑通远程认证。

因此，它可以作为：
- Windows 构建参考
- 消息流参考
- 旧式端到端 RA 流程参考

但不建议在文档里把它写成你的主选技术路线。

### 13.2 在系统设计中新增远程认证流程

5. 后续病历数据仅在安全信道中传输，并在 Enclave 内部解密处理。

### 13.3 在论文表达中新增这几个关键结论

- 远程认证不是普通登录认证，而是“验证远程 Enclave 是否真实可信”。
- 患者不是盲目信任服务器操作系统，而是验证服务器上的 Enclave 身份。
- 认证通过后建立安全信道，中间攻击者即使拦截流量也无法恢复明文病历。
- Sealing 负责“存储态安全”，Remote Attestation 负责“远程访问前的可信验证”，两者共同构成完整安全链路。
