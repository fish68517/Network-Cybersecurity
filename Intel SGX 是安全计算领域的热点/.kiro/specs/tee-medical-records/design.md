# 基于可信执行环境的密态病历信息系统 - 设计文档

## 概述

本系统采用 C/S 架构，基于 Intel SGX 实现医疗数据的全生命周期加密保护。核心设计理念是将所有敏感数据处理逻辑放在 Enclave 内，确保即使系统被攻破，明文数据也永不泄露。

### 系统目标
- 实现数据全生命周期密态保护（静态、传输、使用中）
- 将信任根从庞大 OS 缩小到 Enclave + CPU 硬件
- 在保证安全的前提下，性能接近原生应用

## 核心模块设计

### 模块 1：身份认证与权限管理

#### 1.1 身份认证机制

**基于公钥密码学的认证**
```
客户端                          Enclave
   │                              │
   ├─ 生成随机 Challenge ────────>│
   │                              │
   │<─ 返回 Challenge ────────────┤
   │                              │
   ├─ 用私钥签名 Challenge ──────>│
   │                              │
   │<─ 验证签名，返回 Token ──────┤
   │                              │
   └─ 使用 Token 进行后续操作
```

**实现细节**
- 使用 RSA-2048 或 ECC-256 进行签名
- Challenge 包含时间戳，防止重放
- Token 有有效期限制（如 1 小时）
- 所有认证过程在 Enclave 内完成

#### 1.2 基于角色的访问控制（RBAC）

```
┌─────────────────────────────────────────┐
│           用户角色定义                   │
├─────────────────────────────────────────┤
│ 患者（Patient）                         │
│  - 权限：读写自己的基本信息              │
│  - 权限：只读自己的病历                  │
│  - 权限：查看自己的访问日志              │
├─────────────────────────────────────────┤
│ 医生（Doctor）                          │
│  - 权限：只读患者基本信息                │
│  - 权限：读写患者病历                    │
│  - 权限：查看患者访问日志                │
├─────────────────────────────────────────┤
│ 管理员（Admin）                         │
│  - 权限：系统部署和维护                  │
│  - 权限：无法访问业务数据                │
│  - 权限：查看系统日志                    │
└─────────────────────────────────────────┘
```

**访问控制矩阵**
```
操作类型        患者    医生    管理员
─────────────────────────────────────
读患者基本信息   ✓      ✓       ✗
写患者基本信息   ✓      ✗       ✗

```

### 模块 2：患者基本信息管理

#### 2.1 数据结构设计

```cpp
// Enclave 内的安全数据结构
struct PatientInfo {
    uint32_t patient_id;           // 患者 ID
    char name[256];                // 姓名
    uint8_t age;                   // 年龄
    char gender;                   // 性别
    char phone[20];                // 电话
    char email[256];               // 邮箱
    uint8_t mac[32];               // MAC 用于完整性验证
    uint32_t version;              // 版本号，防重放
    time_t last_modified;          // 最后修改时间
};

// 使用 STL Map 存储患者信息
std::map<uint32_t, PatientInfo> patient_cache;
```

#### 2.2 操作流程

**查询患者信息**
```
1. 客户端发送加密查询请求（包含患者 ID）
2. Enclave 验证请求者身份和权限
3. 从数据库读取加密数据
4. 在 Enclave 内解密
5. 验证 MAC 和版本号
6. 返回数据给请求者（如果权限允许）
7. 清零内存中的明文数据
```

**修改患者信息**
```
1. 客户端发送加密修改请求
2. Enclave 验证请求者身份和权限
3. 从数据库读取旧数据
4. 验证旧数据的 MAC 和版本号
5. 更新数据
6. 计算新的 MAC
7. 增加版本号
8. 加密新数据
9. 写入数据库
10. 清零内存中的明文数据
```

#### 3.2 CRUD 操作

**Create（创建病历）**
```

3. 生成新的 record_id
4. 创建 MedicalRecord 结构

6. 加密数据
7. 写入数据库
8. 返回 record_id
9. 清零内存
```

**Read（查询病历）**
```
1. 用户发送加密查询请求
2. Enclave 验证身份和权限
3. 从数据库读取加密数据
4. 解密并验证 MAC
5. 返回数据
6. 清零内存
```

**Update（修改病历）**
```
1. 医生发送加密修改请求
2. Enclave 验证身份和权限
3. 读取旧数据，验证 MAC 和版本号
4. 更新数据
5. 增加版本号
6. 计算新 MAC
7. 加密并写入数据库
8. 清零内存
```

**Delete（删除病历）**
```
1. 医生发送加密删除请求
2. Enclave 验证身份和权限
3. 读取数据验证
4. 标记为已删除（逻辑删除）
5. 加密并写入数据库
6. 清零内存
```

### 模块 4：密钥管理

#### 4.1 多级密钥体系

```
┌─────────────────────────────────────┐
│      主密钥（Master Key）            │
│  - 在 Enclave 内生成                 │
│  - 使用 Sealing 持久化存储           │
│  - 仅用于派生其他密钥                │
└────────────┬────────────────────────┘
             │
    ┌────────┴────────┬────────────┐
    │                 │            │
┌───▼──────┐  ┌──────▼──┐  ┌─────▼──────┐
│ 用户密钥  │  │ 数据密钥 │  │ 审计密钥   │
│ (User Key)│  │(Data Key)│  │(Audit Key) │
└───┬──────┘  └──────┬──┘  └─────┬──────┘
    │                │            │
    ├─ 患者密钥      ├─ 患者信息  ├─ 审计日志
    ├─ 医生密钥      ├─ 病历数据  │
    └─ 管理员密钥    └─ 临时数据  │
```

#### 4.2 密钥生成与存储

**初始化阶段**
```
1. Enclave 启动时生成主密钥
2. 使用 SGX Sealing 加密主密钥
3. 将 Sealed 数据存储在文件系统
4. 主密钥仅在 Enclave 内存中保存
```

**运行时密钥派生**
```
1. 从主密钥派生用户密钥（使用 HKDF）
2. 从主密钥派生数据密钥
3. 从主密钥派生审计密钥
4. 所有派生过程在 Enclave 内完成
```

#### 4.3 密钥轮换

```
定期密钥轮换流程：
1. 生成新的主密钥
2. 使用新主密钥派生新的数据密钥
3. 遍历所有加密数据
4. 使用旧密钥解密
5. 使用新密钥重新加密
6. 销毁旧密钥
7. 更新 Sealing 数据
```

### 模块 6：性能优化 - Switchless Calls

#### 6.1 传统 ECall/OCall 的性能问题

```
传统 ECall 流程：
1. 用户态 -> 内核态（系统调用）
2. 上下文切换
3. 进入 Enclave
4. 执行函数
5. 退出 Enclave
6. 内核态 -> 用户态
7. 恢复上下文

开销：每次 ECall 约 10,000+ CPU 周期
```

#### 6.2 Switchless Calls 优化

```
共享内存环形缓冲区：

┌─────────────────────────────────────┐
│      共享内存（Shared Memory）       │
├─────────────────────────────────────┤
│  ┌─────────────────────────────┐   │
│  │  环形缓冲区（Ring Buffer）   │   │
│  │  ┌───┬───┬───┬───┬───┐     │   │
│  │  │ 0 │ 1 │ 2 │ 3 │ 4 │ ... │   │
│  │  └───┴───┴───┴───┴───┘     │   │
│  │   ▲                         │   │
│  │   │ 写指针（Write Ptr）     │   │
│  │   │ 读指针（Read Ptr）      │   │
│  └─────────────────────────────┘   │
└─────────────────────────────────────┘

Switchless Call 流程：
1. 不可信代码将请求写入环形缓冲区
2. 设置标志位
3. Enclave 轮询标志位
4. 读取请求并处理
5. 将结果写入缓冲区
6. 设置完成标志
7. 不可信代码读取结果

开销：每次调用约 100-500 CPU 周期（相比 10,000+）
```

#### 6.3 实现策略

```cpp
// 共享内存结构
struct SwitchlessBuffer {
    uint32_t write_ptr;
    uint32_t read_ptr;
    uint32_t size;
    uint8_t data[BUFFER_SIZE];
};

// 请求结构
struct Request {
    uint32_t type;           // 请求类型
    uint32_t param_count;    // 参数个数
    uint8_t params[256];     // 参数数据
    uint32_t result_size;    // 结果大小
};

// 响应结构
struct Response {
    uint32_t status;         // 状态码
    uint8_t result[256];     // 结果数据
};
```

## 安全设计

### 威胁模型

**假设攻击者可以：**
- 完全控制操作系统
- 访问系统内存
- 进行缓冲区溢出攻击
- 部署恶意软件
- 进行物理攻击（但无法破坏 CPU）

**假设攻击者无法：**
- 破坏 CPU 硬件
- 破坏 SGX 硬件实现
- 获得 Intel 的私钥

### 防护措施

#### 1. 内存隔离
- 所有敏感数据仅在 Enclave 内以明文形式存在
- Enclave 外的数据全部加密
- 使用内存清零防止数据残留

#### 2. 访问控制
- 基于角色的访问控制（RBAC）
- 细粒度权限检查
- 操作审计日志

#### 3. 数据完整性
- 使用 MAC 验证数据完整性
- 版本号防止重放攻击
- 时间戳防止时间混乱

#### 4. 密钥保护
- 密钥在 Enclave 内生成
- 使用 Sealing 持久化存储
- 定期密钥轮换
- 密钥销毁时完全清零

#### 5. 身份认证
- 基于公钥密码学
- Challenge-Response 机制
- Token 有效期限制

| 单次查询响应时间 | < 500ms | 用户可接受的响应时间 |
| 系统吞吐量 | > 100 请求/秒 | 支持日常医疗工作 |
| 并发用户数 | ≥ 10 | 支持多用户同时访问 |
| Switchless 性能提升 | ≥ 50% | 相比传统 ECall/OCall |
| 内存占用 | < 500MB | Enclave 内存限制 |
| 系统稳定性 | 24 小时无故障 | 支持长时间运行 |

### 性能优化策略

1. **Switchless Calls**：减少上下文切换开销
2. **缓存优化**：在 Enclave 内缓存热数据
3. **批量操作**：支持批量查询和修改
4. **异步处理**：非关键操作异步处理
5. **内存管理**：优化内存分配和释放
